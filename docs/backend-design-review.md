## 문서 내부 충돌·구현 한계

1. **요청 예시의 Markdown 손상:** 초대 JSON의 URL이 링크 구문으로 감싸져 있어 그대로 JSON 파싱할 수 없다. 또한 공통 장르 예시의 type 누락이 있다. 이후 필드표를 계약 근거로 삼으며 해당 업무 API는 이번에 노출하지 않는다.
2. **관심 PENDING 중복:** 앞 절의 인덱스 예시는 역방향 동일 쌍을 강제하지만 15절 V1은 정책 미확정으로 이를 명시적으로 보류한다. V1에 부분 UNIQUE 인덱스를 임의로 추가하지 않는다. 요청 서비스 출시 전 결정·추가 마이그레이션·동시성 검증이 필요하다.
3. **GENRE 유형:** 일반 FK/CHECK는 참조 태그의 type을 검증하지 못한다. V1의 단순 FK를 유지하고 조인 엔티티 생성 시 GENRE 검사를 한다. DB 직접 쓰기까지 보장한다고 주장하지 않는다. 복합 FK/트리거는 별도 결정 사항이다.
4. **연결 정합성:** accepted_request_id FK는 해당 요청이 ACCEPTED인지, 두 사용자가 같은 쌍인지 보장하지 못한다. 수락 서비스 트랜잭션에서 검증해야 하며 이번에는 그 서비스를 만들지 않는다.
5. **UUID 정렬:** Java UUID.compareTo는 부호 있는 long 비교이므로 PostgreSQL UUID 순서와 달라질 수 있다. 연결 쌍은 unsigned UUID 순서를 쓰는 유틸리티로 정규화하고 PostgreSQL CHECK와 대조한다.
6. **UUID 생성 위치:** V1은 DB 기본 생성기를 두지 않는다. 엔티티 생성자는 호출자가 UUID를 제공하도록 하여 버전·발급 정책을 확정하지 않는다. 테스트 UUID는 테스트 코드에서만 생성한다.
7. **404/410·429 및 보안 검사의 우선순위:** 초대 만료 상태 코드와 요청 제한은 미정이므로 사용하지 않는다. CSRF는 인증·Controller 검증보다 먼저 실행될 수 있어 미인증 변경 요청도 토큰이 없으면 403 CSRF_INVALID가 된다. 유효한 CSRF와 세션이 없는 보호 요청은 401이다.

## 이번 구현 경계

- Java 21, Spring Boot 4.1.2, Gradle 9.5.1을 명시적으로 고정한다. 제품 정책이 아닌 빌드 재현성 선택이다.
- V1 14개 테이블·Entity/Repository, 공통 PageResponse/오류 DTO·예외 처리, JSON 로그인·세션 조회·로그아웃·CSRF 획득을 구현한다.
- 기존 클라이언트가 제안한 `GET /api/v1/auth/csrf`에서 `{token,headerName}`을 반환하는 기술적 획득 경로를 채택한다. 세션 토큰 저장·BREACH 보호·로그인 후 세션 ID 변경·CSRF 교체를 유지한다.
- 가입의 비밀번호/자동 로그인 정책, 취향 COMPLETE 기준, 카탈로그 공개 범위·size 상한, 추천 가중치, 초대 기간·재사용, 관심 재요청·탈퇴 보존 기간은 확정하지 않는다.
- 준비되지 않은 catalog·초대 등 경로를 공개하지 않는다. 인증 기반 이외의 업무 API·음원 데이터/초기 사용자 seed를 만들지 않는다.
- 405/415는 HTTP 프로토콜 오류를 500으로 오인하지 않도록 METHOD_NOT_ALLOWED·UNSUPPORTED_MEDIA_TYPE 코드로 보완한다. 제품 정책 확정이 아니다.
- 사용자가 선택한 임시 PostgreSQL에 V1을 적용해 검증한다. 기존 DB/운영 DB에는 적용하지 않는다.
