## 기본 흐름

**모든 작업 브랜치 → dev → 개발 완료 후 main**

| 브랜치      | 역할                                                              | 반영 기준                            |
| ----------- | ----------------------------------------------------------------- | ------------------------------------ |
| 작업 브랜치 | `frontend`, `feature/*`, `fix/*`, `docs/*` 등 기능·수정 단위 작업 | 최신 `dev`에서 분기하고 `dev`로 통합 |
| `dev`       | 개발 중 코드·문서·테스트의 통합                                   | 작업 브랜치의 검토·검증 결과를 모음  |
| `main`      | 개발 완료 결과                                                    | 사용자 승인 후 `dev`에서 최종 통합   |

개발 중인 작업을 `main`에 직접 올리지 않는다. PR을 사용할 때도 일반 작업의 대상은 `dev`이며, 최종 반영만 `dev → main`으로 한다. 이 문서는 브랜치 보호나 자동 병합 설정을 추가한 것은 아니다.

## 작업 시작

로컬 변경을 보존한 상태에서 최신 `dev`를 기준으로 작업 브랜치를 만든다. 아래는 사용자가 실행을 결정했을 때의 예시다.

```sh
git switch dev
git pull --ff-only origin dev
git switch -c feature/task-name
```

작업을 마치면 Markdown 기록과 한국어 커밋 메시지를 준비한다. 커밋·푸시·병합은 사용자의 명시적 요청 범위에서 수행한다. 요청이 없으면 문서와 제안 메시지만 제공한다.

## 초기 저장소 정리

- 잘못 `main`에 올린 초기 커밋 `25f5410`은 `dev` 이력에 보존한다.
- 미커밋 상태였던 문서 정리와 새 브랜치 규칙도 작업 브랜치를 통해 `dev`에 통합한다.
- `main`은 파일이 없는 기준 커밋 하나로 둔다. Git 브랜치를 유지하기 위한 커밋이며 개발 파일은 없다.
- 이 빈 기준 커밋을 `dev`의 공통 조상으로 연결한다. 이후 `dev → main` 반영에 서로 무관한 이력 병합을 요구하지 않도록 한다.
- 초기 정리에서만 확인된 기존 `main` SHA를 대상으로 이력을 교정한다. 이후 개발에서 `main` 강제 푸시를 기본 절차로 사용하지 않는다.
- 로컬 작업 브랜치는 삭제하지 않으며, 통합 후 현재 작업 위치는 `dev`로 둔다.

정리 결과와 검증은 [브랜치 전환 기록](work-log/2026-11-10-dev-main-workflow.md)에 남긴다.
