# 개발 통합을 dev로 옮기고 main 기준선 정리

- 날짜: 2026-11-10
- 요청: 잘못 올린 `main`을 비우고 모든 기존 작업을 `dev`로 이동. 이후 모든 작업 브랜치 → `dev`, 개발 완료 후 `dev` → `main` 사용.
- 범위: Git 브랜치·이력 정리, 이전 문서 정리 반영, 운영 규칙 문서화. 앱 코드·설정·정적 자산은 변경하지 않음.

## 시작 상태

- 원격 기본 브랜치 `main`에는 초기 커밋 `25f54107bea95fbcc09d2183afc880d94601afab` 하나가 있었다.
- 원격 `dev`는 없었다. 로컬 `main`·`dev`·`frontend`는 모두 같은 초기 커밋을 가리켰다.
- 사용자가 선택한 현재 브랜치는 `frontend`였으며, 이전 Markdown 문서 정리가 미커밋 상태였다.

## 처리 방식

1. 원래 코드가 사라지지 않도록 기존 초기 커밋을 원격 `dev`에 먼저 보존한다.
2. `frontend`에서 문서 정리·브랜치 운영 규칙·이번 기록을 커밋한다.
3. 파일 없는 독립 기준 커밋을 만들고 이를 `dev` 이력에 연결한다.
4. `frontend`를 `dev`로 병합해 기존 코드와 최신 문서를 함께 보존하고 원격 `dev`에 반영한다.
5. `dev` 보존을 확인한 후, 원래 `main` SHA를 지정한 lease로 원격 `main`을 빈 기준 커밋으로 교정한다. 다른 변경이 생겼으면 덮어쓰지 않는다.
6. 로컬 `main`을 원격과 맞추고 현재 브랜치는 `dev`로 둔다.

이 방식은 기존 초기 커밋을 `dev`의 조상으로 보존하고, 빈 `main`도 `dev`의 조상으로 만든다. 개발 완료 시 일반적인 `dev → main` 통합이 가능하다.

## 문서 변경

- [AGENTS.md](../../AGENTS.md)에 작업 브랜치 → `dev` → `main` 규칙 추가.
- [브랜치 운영](../git-workflow.md)에 브랜치 역할·시작 방법·최종 반영·초기 교정 방식 정리.
- 프로젝트/문서 README와 작업 기록 목록에 탐색 링크 추가.
- 이전 [문서 정리](2026-11-10-documentation-cleanup.md) 작업까지 함께 반영. 당시 “커밋·푸시 미수행” 기록은 그 작업 시점의 사실로 보존.

## 검증 기준

사전 검사에서 Markdown 23개·내부 링크/앵커 156개가 통과했고, 초기 커밋의 비 Markdown 파일 84개와 디자인 참고 원본 3개가 그대로 보존됨을 확인했다. 변경은 Markdown에만 있으며 비밀값 패턴·공백 검사도 통과했다.

- 원격 `dev`와 로컬 `dev`의 커밋 일치, 현재 브랜치 `dev`, 미커밋 변경 없음.
- 원격/로컬 `main`에 파일 0개, 빈 기준 커밋 1개.
- 초기 커밋과 `main` 기준 커밋이 모두 `dev`의 조상이며 현재 작업 브랜치도 통합됨.
- 초기 커밋 대비 앱·비 Markdown 파일의 내용 유지, 디자인 참고 원본 보존.
- 문서 링크·형식·공백 검사. 앱 코드 변경이 없어 기존 44개 테스트·빌드 결과를 유지하며 재실행하지 않음.
- 서버 실행·Notion 수정·배포·브랜치 삭제·다른 저장소 변경은 하지 않음.

## 커밋 메시지

```text
chore: dev 중심 브랜치 흐름과 프로젝트 문서 정리

- 미커밋 문서 정리와 디자인 참고 자료 이동 반영
- 모든 작업 브랜치의 통합 대상을 dev로 명시
- 개발 완료 후에만 dev에서 main으로 반영하도록 기록
- 기존 작업과 초기 커밋을 dev에 보존하는 이력 정리 문서화
```

기준선·병합 커밋은 각각 `chore: main을 위한 빈 기준선 생성`, `chore: 빈 main 기준선을 dev 이력에 연결`, `merge: frontend 작업과 문서 정리를 dev에 통합` 메시지를 사용한다.
